# 데이터 건수 셈법 — 칸 단위 vs 타겟(Y) 단위 (2026-10-14 논의 · 정의 확정)

> 상태: **셈법 정의 = 확정(사용자 10-14)**. 보고·평가에 어느 셈법을 쓸지는 **보류** — 넷 다 추산해 두고 그때 고른다.
> 계산 = `scripts/count_methods.py`(ChemDX 실데이터 + 트리플) · `scripts/lab_estimate.py`(랩별 registry 레시피 추산).
> 숫자 = `reports/count-methods-<빌드>.md` · `reports/lab-estimate-registry-v<판>.md`.

## 배경

- 전략연구사업은 5개 분야 소재 실험 데이터를 온톨로지 기반으로 모은다. 계획서는 **실험 한 건 = 한 세트**로 보고,
  세트마다 조성·구조·공정·분석 건수를 추산해 더해 **5년 10만 건**으로 잡았다(2026 = 455세트 · 5,900건).
- 지금 sdl-prefill `sheets.data_counts`(웹 화면·정량지표 공용)는 **채워진 칸 하나 = 1건**이다(registry 기본값 포함).
- 10-14 주변 연구자 토의의 반론: 한 실험에서 바뀌는 변수는 한두 개뿐인 경우가 많은데, 그대로인 공정 변수·CAS·화학식까지 칸마다 1건으로
  세는 것이 맞나? → AI 모델링의 **타겟(Y)만 따로 세고**, 거기까지 거친 **피처(X)는 묶어서** 세야 한다는 논리.
- 두 논리 모두 근거가 있어 **둘 다 추산해 두고** 나중에 고르기로 했다.

## 정의(확정)

| 셈법 | 정의 |
|---|---|
| **A** 칸 단위 | 채워진 칸 = 1건(조성 = 개체 정보 칸 · 공정 = 파라미터 + 투입량 · 분석 = 측정값·파일). 현행 `data_counts` 그대로 |
| A′ | A 에서 registry 기본값(Source=default) 칸을 뺌 = 연구자가 적은 칸만 |
| **B** 범주 + Y(반복마다) | 조성 1 + 구조 1 + 공정 1(있을 때) + **Y 를 반복 측정 횟수만큼** |
| **C** X 1 + Y(항목마다) | X 1 + **Y 를 측정 항목(스텝·결과 이름)마다 1** — 반복은 묶음 |
| (참고) ML 표본 행 | Y 를 낸 측정(스텝·반복) 하나 = 1 — 학습 데이터의 행 수 |

**Y** = Value 시트의 **측정 결과 행 하나 = 1건**.
- 숫자·파일 가리지 않는다 — **파일 하나 = Y 1건**. 측정 비정형 데이터 하나에서 Y 가 여러 개 나올 수 있으니 보수적 셈이다.
- **파일과 그 파일에서 뽑은 숫자는 둘 다 센다**(JV 곡선 1 + PCE·Jsc·Voc·FF 4 = 5). 파일마다 따로 규칙을 두면 끝이 없다.
- XRD 결정크기·상분율 같은 **물성도 성능과 같은 Y**. 전환율·수율·쿨롱효율도 Y(물성·성능).
- **예외 하나**: 랩이 registry Kind 에 **공정(Process)** 이라고 적은 결과 = 공정 중 실측값(칭량 질량 · 압력·온도 로그 등) → **X**.
  기준은 랩 표기 — MPSP 매핑이 바꾼 Kind 가 아니다(BAS 전환율·수율은 MPSP 로는 process 지만 랩 표기 Performance → Y).

**X 범주(B)**
- 조성 = 개체 정보 칸이 있으면 1 · 공정 = 파라미터·투입량이 있으면 1.
- **구조 = 구성(structure/configuration)** — 부분들이 어떻게 짜였는가(적층 순서 · 소자 형식 · 셀 형식).
  **산출물이 부품·소자(플랫폼 J2 판정 component·device)면 1**, 분말·용액 같은 재료면 0. 랩마다 손으로 정하지 않는다.
  측정으로 얻은 구조값(XRD 등)은 Y.

## 트리플(지식그래프)

- 플랫폼 적재기(`sdl-ontology-platform` `v05.load`)로 실제 그래프를 만들어 센다(Entity Type = 플랫폼 J2) — 태양전지 170세트 = 340,431.
  Y 측정 결과 행 하나 ≈ 14 트리플 · 공정 칸 하나 ≈ 10 · 기본값 칸도 노드가 된다.
- 트리플 수는 **셈법과 무관한 한 그래프의 크기**이고 모든 칸이 노드가 되므로 성격이 A 에 가깝다 → **건수와 섞지 않고 별도 지표**.
- 조건: prefill 5sheet-1.1 → 플랫폼 v0.6 시트 이름만 바꿔 넣음. registry 추가후보·조성 constituent 행이 들어오면 트리플은 늘어난다.

## 랩 확인 목록(B·C 추산을 범위가 아닌 값으로 만들려면)

1. **세트당 반복 측정 수**(B) — 계획 달성에 필요한 수: PCC 3 · PSC(RCP-01·02) 2 · CAM 4 · BAS-01 3. "실제로 세트당 몇 번 재나?"
2. **PCC 칭량 질량 5개의 Kind = '물성'** — 공정 기록이면 '공정'으로 고쳐야 X 가 된다(지금은 Y 로 잡힘). PCC registry 회신 때.
3. **BAS 개체 J2 판정 없음**(RCP-01 5개 · RCP-02 3개) — 지금 구조 0 으로 셈. 플랫폼 J2 에서.
4. **OPD 레시피 결과 정의**(Recipe 행에 RecipeCode·결과가 없다) — 정의되면 추산 가능.

## 열린 것

- 보고·평가 때 어느 셈법을 쓸지(또는 병기) · 트리플을 별도 지표로 낼지.
- 셈법이 정해지면 sdl-prefill `data_counts` 에 B·C 셈을 넣을지(웹 화면과 같은 셈이 되도록 — 그쪽 일).
