# 데이터 건수 셈법 — 칸 단위 vs 타겟(Y) 단위 (2026-10-14 논의)

> 상태: **둘 다 추산해 두고, 평가·보고서를 쓸 때 골라 쓴다**(결정 보류). 이 레포에 기록하기로 한 것은 사용자 결정(10-14).
> 계산 = `scripts/count_methods.py` · 숫자 = `reports/count-methods-<빌드>.md`.

## 배경

- 전략연구사업은 5개 분야 소재 실험 데이터를 온톨로지 기반으로 모은다. 계획서는 **실험 한 건 = 한 세트**로 보고,
  세트마다 조성·구조·공정·물성/성능 정보를 추산해 더해 **5년 10만 건**으로 잡았다.
- 지금 sdl-prefill `sheets.data_counts`(웹 화면·정량지표 공용, 10-14 정의)는 **채워진 칸 하나 = 1건**이다(registry 기본값 포함).
- 10-14 주변 연구자 토의에서 나온 반론: 한 실험에서 바뀌는 변수는 한두 개뿐인 경우가 많다. 나머지 공정 변수·CAS·화학식은 그대로인데,
  그것까지 칸마다 1건으로 세는 것이 맞나? → AI 모델링의 **타겟 물성(Y)만 따로 세고**, 그 값이 나오기까지 거친
  **피처(X: 조성·공정 변수 등)는 묶어서 1건**으로 봐야 한다는 논리.
- 두 논리 모두 근거가 있어 **둘 다 추산해 두고** 나중에 고르기로 했다.

## 셈법

| 이름 | 정의 | 성격 |
|---|---|---|
| **A** 칸 단위 | 채워진 칸 = 1건(조성 = 개체 정보 칸 · 공정 = 파라미터 + 투입량 · 분석 = 측정값·파일). 현행 `data_counts` | 최대치 |
| A′ | A 에서 registry 기본값(Source=default) 칸을 뺌 = 연구자가 적은 칸만 | 중간 |
| **B** 범주 묶음 + Y | 세트마다 조성·구조·공정이 있으면 각 1건 + **Y 값마다 1건** | |
| **C** X 한 건 + Y | 세트마다 X 1건 + **Y 값마다 1건** | 최소에 가까움 |
| (참고) ML 표본 행 | Y 를 낸 측정(스텝·반복) 하나 = 1건 — 학습 데이터의 행 수 | |

**X/Y 를 가르는 규칙(5개 랩 공통으로 쓸 수 있게 제안)**: Value 시트의 **측정값(파일 아님) = Y**, 측정 파일 = 원자료(따로 셈),
나머지(Entity·Process·Parameter) = X. `data_counts` 의 분석 칸을 값과 파일로만 나누면 바로 셀 수 있다.

애매한 것(질문에 따라 역할이 바뀜):
- **측정 조건**(셀 면적·광세기·스캔 방향) — X 도 Y 도 아닌 Y 의 조건. 5시트에선 Parameter 행이라 X 묶음에 들어간다.
- **측정 원자료 파일**(JV 곡선) — Y 를 계산해 낸 원자료이지 Y 자체는 아니다. B·C 에 넣을지 따로 둔다.
- **중간 분석값**(XRD·PL·UV-Vis·두께 등) — 재료 물성이 질문이면 Y, 소자 성능이 질문이면 X(기술자). 규칙상으로는 Value 측정값이라 Y.
- `data_counts` 는 Value 의 Kind 가 Structure·Material Entity 면 구조·조성으로 센다 — B 에서 이 값을 X 범주로 볼지 Y 로 볼지는
  그런 데이터가 있는 랩에 적용할 때 정한다(2026 태양전지에는 없음).

## 태양전지(KRICT PSC, ChemDX 2026)에 적용

- **Y** = JV 성능 4종(PCE·Jsc·Voc·FF), 셀·스캔 방향마다. 아직 라이브러리에 없는 후보 = Rs·Rsh·Pmax·Vmp/Jmp(`mapping/psc_additions.csv`) ·
  히스테리시스(유도값) · 안정성(2026 데이터 없음).
- **X** = 페로브스카이트 조성식 · 층별 재료 · 공정 조건(스핀·열처리·반용매·분위기·실험실 온습도) · 측정 조건.
- 결과(`reports/count-methods-dev-20261014b.md`, 170세트): **A 28,398 · A′ 18,998 · B 9,652 · C 9,482**(ML 표본 행 2,328).
  A : C ≈ 3 : 1 — 태양전지는 실험 하나에 셀이 평균 14개라 Y 가 많아서 3배에 그친다. 공정 칸이 많고 결과가 하나(수율 등)인 실험이면
  차이가 수십 배가 된다 → **셈법에 따라 랩별 비중이 크게 달라진다**.
- 반론을 뒷받침하는 숫자: A 의 공정 16,588건 중 9,400건(57%)이 registry 기본값. 공정 파라미터 자리 128 중
  세트마다 값이 실제로 달라지는 자리는 22(Process Note 에만 있는 몰농도 등 제외).

## 트리플(지식그래프)

- 플랫폼 적재기(`sdl-ontology-platform` `v05.load`)로 실제로 그래프를 만들어 센다 — 170세트 = **339,921 트리플**(세트당 약 2,000, 미표현 0).
  Y 값 하나 ≈ 15 트리플(측정 행위·값·수량값·MPSP 참조·소자 귀속) · 공정 칸 하나 ≈ 10 · 기본값 칸도 노드가 된다.
- 트리플 수는 **셈법과 무관한 한 그래프의 크기**이고, 모든 칸이 노드가 되므로 성격이 A 에 가깝다 → "건수"와 섞지 말고 따로 둔다.
- 조건: prefill 5sheet-1.1 → 플랫폼 v0.6 시트 이름만 바꿔 넣음 · Entity Type(J2) 은 잠정 규칙. registry 추가후보·조성 constituent 행이
  들어오면 트리플은 늘어난다.

## 열린 것

- 보고·평가 때 어느 셈법을 쓸지(또는 병기) · 원자료 파일을 셀지 · 트리플을 별도 지표로 낼지.
- 셈법이 정해지면 sdl-prefill `data_counts` 에 B·C 셈을 넣을지(웹 화면과 같은 셈이 되도록 — 그쪽 일).
